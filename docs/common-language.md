# 通用语言 - 基于 RAG 的多模态电商智能导购 Agent

> 最后更新：2026/05/12  
> 参与者：项目开发者、AI 辅助开发者、比赛评审视角

## AI 当前理解框架

基于需求描述，我理解这是一个“电商业务系统 + RAG Agent + 多模态检索”的全栈比赛项目。

我的理解框架是：

```text
用户自然表达/图片
  → Agent 理解意图
  → 检索商品知识
  → 生成可解释推荐
  → 调用电商业务接口完成加购/结算
```

可能的理解偏差：我会倾向把它设计成“可运行的业务闭环系统”，而不是只做一个演示型聊天机器人。如果比赛更看重视觉演示或模型创新，后续需要调整优先级。

## 核心概念

| 术语 | 本项目中的含义 | 不是什么 | 澄清记录 |
|------|---------------|----------|----------|
| 智能导购 Agent | 能理解用户需求、主动检索商品、解释推荐理由并触发业务动作的 AI 应用 | 不是只回答闲聊问题的 Chatbot | 必须对接商品、库存、购物车等真实业务链路 |
| RAG | 先从商品知识库中检索相关信息，再把结果交给大模型生成回复 | 不是只依赖大模型参数记忆 | 用于降低幻觉，并让推荐基于真实商品数据 |
| 多模态 | 同时处理文字和图片输入，例如参考穿搭图 + 预算描述 | 不是单纯支持图片上传 UI | 图片需要参与检索或特征理解 |
| Offline Knowledge Pipeline | 离线把商品、库存、类目、评价、图片等数据处理成可检索知识 | 不是实时聊天逻辑 | 服务于在线检索质量和召回效率 |
| Online RAG Engine | 实时处理用户请求，完成意图识别、检索、Prompt 组装和结果解析 | 不是商品 CRUD 后端 | 负责 AI 决策和推荐生成 |
| 电商微服务底座 | 承载商品、库存、购物车、结算等确定性业务逻辑的 Spring Boot 服务 | 不是 AI 推理服务 | Agent 只能通过它完成真实业务动作 |
| 商品中心 | 管理 SPU/SKU、价格、类目、属性、图片等商品数据 | 不是推荐算法模块 | 为检索和交易链路提供基础数据 |
| SPU | 标准商品单元，例如“某品牌某款连衣裙” | 不是具体可购买规格 | 前端推荐卡片通常按 SPU 展示 |
| SKU | 具体可购买规格，例如颜色、尺码组合 | 不是商品概念页本身 | 加购、库存校验、结算应以 SKU 为准 |
| 混合检索 | 结合向量相似度检索和 SQL/条件过滤 | 不是只查向量数据库 | 价格、库存、类目等硬条件必须可控 |
| 向量检索 | 把文本/图片转成向量后做语义相似度匹配 | 不是关键词匹配 | 适合处理“类似这张图”“通勤风”等模糊需求 |
| SQL 过滤 | 用结构化条件筛选商品，例如价格区间、库存状态、类目 | 不是语义理解 | 用于保证推荐符合预算、库存等硬约束 |
| Chunking | 把长商品描述、评价等切成适合检索的文本片段 | 不是随便按字数截断 | 目标是保留语义完整性，避免上下文断裂 |
| Prompt 组装 | 把用户问题、历史对话、检索结果和输出格式要求组合给大模型 | 不是把所有数据都塞进上下文 | 需要控制 Token，减少 Attention 偏移 |
| 结构化输出 | 大模型除自然语言外，还输出可解析 JSON，例如推荐 SPU ID 列表 | 不是自由文本回复 | 前端商品卡片、加购按钮依赖结构化字段 |
| 归因解释 | 说明为什么推荐某商品，例如风格、预算、评价、库存、搭配度 | 不是泛泛夸商品好 | 是比赛亮点，可转成雷达图或数据化洞察 |
| 业务闭环 | 用户从咨询到推荐、加购、结算都能在系统内完成 | 不是只展示推荐列表 | 区分“Demo Chatbot”和“真实导购系统”的关键 |
| 库存校验 | 在推荐、加购、结算前后确认商品可售数量 | 不是只显示库存数字 | 防止推荐不可买商品或并发超卖 |
| 全局异常处理 | AI 超时、JSON 解析失败、数据库异常等统一兜底 | 不是简单返回 500 | 保证演示时系统不崩，用户收到友好话术 |
| TDD | 先写能描述行为的测试，再写实现让测试通过 | 不是补几个测试文件 | 重点覆盖 RAG 召回质量和交易金额计算等核心链路 |
| M-M-M-S 架构 | AI 引擎按 Method、Model、Module、Service 四层组织 | 不是 Spring MVC 的 Controller/Service/DAO | 用于控制 AI 逻辑边界和上下文传递 |

## 概念关系

```text
用户
  → 提供 → 文本需求 / 参考图片 / 预算 / 偏好
  → 触发 → Online RAG Engine

Online RAG Engine
  → 进行 → 意图识别
  → 调用 → Hybrid Search
  → 组装 → Prompt
  → 解析 → 结构化推荐 JSON
  → 调用 → 电商微服务底座

Offline Knowledge Pipeline
  → 抽取 → MySQL 商品/库存/类目/评价数据
  → 清洗切块 → 商品知识 Chunk
  → 向量化 → 文本向量 / 图片向量
  → 写入 → 向量数据库

电商微服务底座
  → 管理 → 商品中心
  → 校验 → 库存
  → 执行 → 加购 / 结算

推荐结果
  → 包含 → 商品卡片
  → 包含 → 推荐理由
  → 可视化 → 归因雷达图/特征权重
```

## 决策背后的推理

### 把 Agent 定义为“可执行导购”而非“聊天机器人”
- **背景**：需求强调业务闭环和加购/结算。
- **选项**：只做自然语言推荐；或让 Agent 输出可执行结构化指令。
- **选择**：采用结构化输出 + 后端业务 API 执行。
- **理由**：这样能展示真实电商系统能力，也能降低大模型幻觉直接影响交易逻辑的风险。

### 把混合检索作为推荐核心
- **背景**：用户需求既有模糊语义，也有预算、库存等硬约束。
- **选项**：只用向量检索；只用 SQL 筛选；混合检索。
- **选择**：混合检索。
- **理由**：向量检索负责“像不像”，SQL 过滤负责“能不能买、符不符合条件”。

### 把 Java 与 Python 边界分开
- **背景**：项目同时需要交易稳定性和 AI 生态能力。
- **选项**：全部 Java；全部 Python；Java 业务后端 + Python AI 服务。
- **选择**：Java 负责电商底座，Python 负责 AI 编排和数据处理。
- **理由**：Spring Boot 更适合业务交易链路，FastAPI 更适合快速接入 Embedding、向量库和模型工具链。

### 把归因解释定义为推荐解释能力
- **背景**：需求提到 LightGBM / SHAP 思路，但比赛项目时间有限。
- **选项**：实现完整机器学习归因；或先实现基于特征权重的解释层。
- **选择**：先定义为“可结构化展示的推荐理由”，算法复杂度可迭代。
- **理由**：评审能直观看到解释价值，同时避免早期被复杂模型训练拖慢闭环建设。

## 建议的 MVP 语义边界

第一阶段 MVP 应做到：

```text
用户输入文字/图片
  → 意图识别为商品推荐
  → 混合检索召回商品
  → LLM 生成推荐理由和结构化 JSON
  → 前端展示商品卡片
  → 用户点击加购
  → Java 后端完成 SKU 库存校验和购物车写入
```

第一阶段暂不强求：

- 真实支付
- 完整分布式微服务治理
- 复杂机器学习归因训练
- 大规模生产级数据同步调度
- 全量售后客服知识库

## 面向计算机专业学生的实现定位

本项目不应只被包装成“调用大模型 API 的应用”，而应体现计算机专业能力：数据建模、后端工程、检索算法、系统集成、测试验证和可解释推荐。

## 推荐系统实现详细计划

### 推荐目标定义

第一版推荐系统先解决三个问题：

1. **能找对**：根据用户自然语言、预算、类目、风格、图片线索召回候选商品。
2. **能筛掉**：过滤无库存、超预算、不符合硬性条件的商品。
3. **能说清**：输出推荐理由、匹配特征和可解释分数，支撑前端展示。

推荐结果建议采用结构化格式：

```json
{
  "intent": "recommend_product",
  "query_summary": "通勤场景、预算 300 元以内、偏简约风",
  "recommendations": [
    {
      "spu_id": 1001,
      "sku_id": 2001,
      "score": 0.86,
      "reason": "价格在预算内，风格标签与通勤/简约匹配，当前库存充足",
      "matched_features": ["通勤", "简约", "300元以内", "有库存"],
      "risk_flags": []
    }
  ]
}
```

### 数据准备阶段

| 步骤 | 任务 | 具体做法 | 输出 |
|------|------|----------|------|
| 1 | 建商品基础数据 | 准备 50-200 个商品，覆盖服饰、美妆、数码或自选垂类 | `product`、`sku`、`category` 表 |
| 2 | 补充可推荐字段 | 为商品添加风格、场景、人群、价格带、材质、卖点、图片 URL | 商品属性字段或 JSON 扩展字段 |
| 3 | 构造商品知识文本 | 将商品标题、属性、卖点、评价摘要拼成可检索文本 | `product_knowledge_chunk` |
| 4 | 生成向量 | 使用文本 Embedding；图片先可用标签文本化，后续再接 CLIP | 向量库 collection |
| 5 | 写种子测试集 | 准备 20 条典型用户需求和期望召回商品 | 推荐评测用例 |

商品知识文本建议格式：

```text
商品：简约通勤白衬衫
类目：女装/衬衫
价格：199
风格：简约、通勤、百搭
场景：上班、面试、日常
卖点：抗皱、亲肤、可机洗
库存：充足
评价摘要：版型合身，适合职场穿搭
```

### 召回与过滤阶段

推荐链路建议分为四层：

```text
用户输入
  → 意图解析：提取类目、预算、风格、场景、禁忌条件
  → 候选召回：向量 TopK + 关键词/类目召回
  → 硬条件过滤：价格、库存、类目、SKU 可售状态
  → 排序解释：计算综合分，生成推荐理由
```

综合评分第一版可以用规则权重，避免一开始陷入复杂模型训练：

```text
score = 0.40 * 语义相似度
      + 0.20 * 预算匹配度
      + 0.20 * 风格/场景匹配度
      + 0.10 * 评价质量
      + 0.10 * 库存健康度
```

各分数定义：

| 分数 | 计算方式 | 示例 |
|------|----------|------|
| 语义相似度 | Embedding cosine similarity | “通勤衬衫”匹配“职场白衬衫” |
| 预算匹配度 | 价格越接近且不超过预算越高 | 预算 300，价格 199 得高分 |
| 风格/场景匹配度 | 用户标签与商品标签交集占比 | 用户要“简约”，商品含“简约/百搭” |
| 评价质量 | 评分、好评关键词、销量等归一化 | 高评分且评价稳定得高分 |
| 库存健康度 | 有库存得分，低库存降权，无库存过滤 | 库存 0 直接排除 |

### Java 后端实现计划

| 模块 | 职责 | 核心接口 |
|------|------|----------|
| ProductController | 商品查询、商品详情 | `GET /api/products/{id}` |
| InventoryController | SKU 库存查询与校验 | `GET /api/inventory/sku/{skuId}` |
| CartController | 加购、修改数量、删除 | `POST /api/cart/items` |
| OrderController | 结算预览、创建订单 | `POST /api/orders/preview`、`POST /api/orders` |
| RecommendationBridgeController | 给 AI 服务提供安全的商品/库存查询接口 | `POST /api/recommendation/candidates` |

Java 后端必须保证：

- AI 只能推荐商品，不能直接修改库存或订单金额。
- 加购前必须校验 SKU 是否存在、是否上架、库存是否足够。
- 结算金额由 Java 后端重新计算，不能相信 AI 返回的价格。
- 所有异常通过全局异常处理返回稳定格式，例如 `code/message/requestId`。

### Python AI 服务实现计划

| 模块 | 职责 | 输入 | 输出 |
|------|------|------|------|
| IntentParser | 提取用户意图和约束 | 用户文本/图片标签 | 类目、预算、风格、场景 |
| Retriever | 调用向量库和后端候选接口 | 查询文本、过滤条件 | 候选商品列表 |
| Ranker | 计算综合推荐分 | 候选商品、用户约束 | 排序后的商品 |
| PromptBuilder | 组装 RAG Prompt | 用户问题、商品上下文 | LLM 输入 |
| OutputParser | 校验结构化输出 | LLM 回复 | 可渲染 JSON |
| ToolClient | 调用 Java 商品/库存接口 | 商品 ID、SKU ID | 实时业务数据 |

AI 服务接口建议：

```text
POST /ai/recommend
请求：用户文本、图片标签/图片 URL、用户上下文
响应：推荐商品列表、推荐理由、匹配特征、可执行动作建议
```

推荐页应让评审直观看到“AI 推荐不是黑盒”：

| UI 区域 | 展示内容 | 价值 |
|---------|----------|------|
| 对话输入区 | 文本、图片上传、预算/偏好输入 | 展示多模态交互 |
| 推荐卡片区 | 商品图、价格、库存、加购按钮 | 展示电商闭环 |

| 链路调试区 | 意图解析、召回数量、过滤数量 | 答辩时展示技术深度 |

### TDD 验收用例

| 测试类型 | 用例 | 期望结果 |
|----------|------|----------|
| 意图解析测试 | “300以内通勤包” | 提取预算 `<=300`、场景 `通勤`、类目 `包` |
| 检索测试 | “类似图片里的简约白衬衫” | 返回含“简约/白衬衫/通勤”标签商品 |
| 过滤测试 | 候选商品含无库存 SKU | 无库存商品不进入最终推荐 |
| 排序测试 | 两个商品都相关，一个超预算 | 预算内商品排名更高 |
| 结构化输出测试 | LLM 返回多余文本 | Parser 能拒绝或修复为合法 JSON |
| 加购测试 | 推荐商品 SKU 库存不足 | Java 后端拒绝加购并返回明确错误 |
| 金额测试 | AI 返回错误价格 | 订单预览仍以后端数据库价格计算 |

### 分阶段里程碑

| 阶段 | 时间建议 | 目标 | 完成标志 |
|------|----------|------|----------|
| P0 | 第 1-2 天 | 明确商品垂类、数据表、接口边界 | ER 图 + API 草案完成 |
| P1 | 第 3-5 天 | 跑通商品、库存、购物车基础链路 | 前端可查商品并加购 |
| P2 | 第 6-8 天 | 完成文本 RAG 推荐 | 输入自然语言能返回商品卡片 |
| P3 | 第 9-10 天 | 加入图片标签/图片向量能力 | 上传图片能影响推荐结果 |
| P4 | 第 11-12 天 | 完成可解释推荐展示 | 推荐卡片带理由和匹配分数 |
| P5 | 第 13-14 天 | 完成测试、异常兜底、演示脚本 | 一条完整演示链路稳定通过 |

### 比赛展示脚本建议

```text
1. 用户上传一张简约通勤穿搭图片，并输入“预算 300，适合面试”。
2. 系统解析出：场景=面试/通勤，风格=简约，预算<=300。
3. RAG 检索商品知识库，过滤无库存和超预算商品。
4. 前端展示 3 个推荐商品，每个都有推荐理由和匹配标签。
5. 用户点击加购，Java 后端校验 SKU 库存并写入购物车。
6. 用户进入结算预览，后端重新计算金额，形成业务闭环。
```

## 后续维护规则

每当出现以下情况，应更新本文档：

1. 引入新的业务术语，例如“搭配套装”“尺码推荐”“用户画像”。
2. 决定具体模型或向量库，例如 CLIP、Milvus、Chroma。
3. 发现 AI 输出与预期不一致，说明某个概念边界没定义清楚。
4. 从比赛规则中获得新的评分标准或限制条件。
